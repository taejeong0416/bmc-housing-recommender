# 부산 공공임대 추천서비스 최종 태그 체계 및 산출 가이드

> 최종 정리일: 2026-07-26  
> 공간 범위: **부산광역시 전체**  
> 최종 검증 입력: 부산도시공사 2026-06-30 전체 6종, 선도소프트 2024 부산 전체 GIS 3종, 모집공고 5건, 부산 전역 공개 외부데이터  
> 산출 코드: `tag/src/`  
> 산출 결과: `tag/output/`

이 문서는 **무슨 태그를 어떤 역할과 규칙으로 사용하는지**를 설명한다. 원천 결측, 이상치, 좌표 복구, 공고 연결 품질 등 **데이터가 어떤 전처리를 거쳤는지**는 `docs/데이터_전처리_품질보고서.md`를 먼저 읽는다. 두 문서를 함께 읽으면 기획자가 전처리 결과와 태그 활용 원칙을 연결해서 이해할 수 있다.

## 1. 최종 결정 요약

태그는 한 목록으로 섞지 않고 역할에 따라 다음처럼 사용한다.

| 분류 | 의미 | 서비스 역할 | 추천모델 가중치 |
|---|---|---|---:|
| A. 자격·유형 | 이 공고·공급트랙에 신청 가능한가 | 하드필터, 확인상태 표시 | 0 |
| B. 주거물리 | 가격·면적·방수·준공·엘리베이터 등 집 자체의 조건 | 사전 희망조건 필터, 사실 표시, 선택적 동률해소 | 원칙 0 |
| C. 입지·교통 | 철도 접근 등 위치의 이동 특성 | 취향학습·추천 | 사용 |
| D. 생활환경 | 카페·운동·마트·외식·문화·조용함·공원·대학가 등 생활권 특성 | 취향학습·추천·설명 | 원자축만 사용 |
| 결합태그 | 둘 이상의 근거를 사람이 이해하기 쉬운 문장으로 요약 | 추천 사유·탐색·카드 카피 | **0** |

핵심 원칙은 다음과 같다.

1. **A와 B는 온보딩 전에 거른다.** 사용자가 감당할 수 없는 가격이나 신청 불가능한 매물을 취향 테스트에서 비교하지 않는다.
2. **취향 가중치는 C와 D의 원자 특징으로만 학습한다.**
3. **결합태그는 설명 전용이다.** 원자 특징으로 이미 계산된 값을 결합태그로 다시 더하지 않는다.
4. **데이터가 없으면 0점이 아니라 `null`이다.** 도로 기준점으로 복구한 저신뢰 좌표 50개와 조용함 격자근거 미확보 후보를 “시설이 없는 곳”으로 오판하지 않는다.
5. **후보 내 백분위를 쓰지 않는다.** 후보가 갱신돼도 같은 거리·같은 시설 수가 같은 점수를 갖도록 고정 거리감쇠식을 사용한다.
6. **부산 전체가 최종 공간 범위다.** 수영구 전용 필터는 제거됐으며 기장·강서까지 포함하는 부산 좌표 검증 범위를 사용한다.

## 2. 추천에 실제로 학습할 최종 취향 벡터

초기 MVP의 **기본 A/B 비교학습**에는 핵심 특징 8개를 사용한다.

| ID | 표시명 | 출처 |
|---|---|---|
| `rail_access` | 도시철도 접근성 | C |
| `cafe_choice` | 카페 선택지 풍부 | D |
| `fitness_access` | 운동시설 가까움 | D |
| `supermarket_access` | 마트 가까움 | D |
| `restaurant_choice` | 외식 선택지 풍부 | D |
| `culture_access` | 문화·여가 가까움 | D |
| `quiet_residential` | 조용한 주거환경 추정 | D |
| `park_walk` | 공원 산책 가까움 | D |

이 8개를 택한 이유는 다음과 같다.

- 사용자가 실제로 취향 차이를 느끼기 쉽다.
- A/B의 자격·가격·면적과 역할이 겹치지 않는다.
- 현재 데이터에서 계산 근거를 설명할 수 있다.
- 가상 매물 A/B 비교 카드에서 서로 다른 생활상을 만들기 좋다.
- 너무 많은 유사 특징을 동시에 학습해 작은 선택 횟수로 불안정한 가중치를 만들 위험을 줄인다.

다만 공공임대의 청년·신혼·고령자·주거취약계층을 함께 고려하면 의료 접근을 단순 설명값으로만 두는 것도 적절하지 않다. 따라서 D에는 다음 **조건부 개인화 특징**을 추가한다.

| ID | 표시명 | 개인화 방식 |
|---|---|---|
| `medical_daily_access` | 병원·약국이 가까운 일상 의료생활권 | 기본 A/B 8축에는 자동 투입하지 않고, 사용자가 기본입력·취향보정에서 의료 접근을 중요하다고 명시한 경우 활성화 |
| `emergency_access` | 응급의료기관 접근성 | 응급 접근이 중요하다고 명시된 경우의 보조 순위·설명 근거. 실시간 진료 가능 여부를 뜻하지 않음 |

즉 모델은 **기본 8축 + 선택형 의료축** 구조다. 나이, 임대유형, 소득계층만 보고 의료 선호를 자동 추정하지 않는다. 이는 고령자에게 의료를 강제하고 청년에게 의료를 무시하는 식의 고정관념을 막으면서도, 실제로 의료 접근이 중요한 사용자의 순위에는 반영하기 위한 설계다.

다음 특징도 산출하지만 추천모델에는 독립 가중치로 중복 투입하지 않는다.

- `metro_access`, `donghae_access`, `bgl_access`, `transfer_access`: `rail_access`의 설명 구성요소
- `bus_stop_proximity`: 버스 서비스가 아닌 정류소 근접 근거
- `cvs_access`, `market_complex_access`, `laundry_access`: 생활편의 설명·결합 구성요소
- `retail_access`: 여러 소매업종을 포괄해 다른 상권 특징과 상관이 높음
- `nightlife_access`: `quiet_residential` 산출에 이미 반영되는 반대축 근거
- `university_walk_access`: 공식 대학 대표주소 접근성 근거
- `university_life_mix`: 카페·외식·편의점·세탁·문화 점수로 본 학생생활형 상권 구성
- `university_commercial_area`: 앞의 두 조건을 함께 만족한 `대학가 생활권` 설명 태그

`nightlife_access`는 “밤에도 활기찬 동네”라는 카드 표현에는 사용할 수 있다. 다만 동일 모델에서 `quiet_residential`과 별도 가중치로 동시에 학습시키면 사실상 같은 축을 두 번 세는 문제가 생길 수 있으므로, MVP에서는 하나의 조용함↔활기 축으로 다룬다.

## 3. A. 자격·유형 태그 최종안

### 3.1 역할

A는 추천 취향이 아니라 **지원 가능성 확인 계층**이다. 판정 단위는 단지 하나가 아니라 아래 조합이어야 한다.

`공고(notice) + 단지(complex) + 주택형(unit type) + 공급대상(track) + 순위(rank)`

같은 단지라도 청년·대학생·고령자·신혼부부 공급의 기준과 가격이 다를 수 있으므로 단지 ID만으로 자격을 확정하면 안 된다.

### 3.2 최종 표시 태그

#### 임대유형

- `행복주택`
- `통합공공임대`
- `매입임대`
- `재개발임대`
- `영구임대`
- `기타공공임대`

#### 공급대상

- `대학생`
- `청년`
- `신혼·한부모`
- `고령자`
- `주거급여수급자`
- `산단근로자`
- `일반`
- `기타·공고확인필요`

공급대상은 추천점수를 올리는 특징이 아니다. 사용자 프로필과 공급트랙을 연결하고, 카드에 “청년 공급”, “고령자 공급”처럼 사실을 표시한다.

### 3.3 자격 판정 상태

| 상태 | 의미 | 서비스 처리 |
|---|---|---|
| `likely_eligible` | 구조화된 모든 필수조건을 통과 | 후보 유지, “신청 가능성 높음” |
| `conditional` | 일부 서류·가구·지역·자산 조건 추가 확인 필요 | 후보 유지, 확인사항 표시 |
| `ineligible` | 명시된 필수조건 하나 이상 불충족 | 기본 후보에서 제외 |
| `unverified` | 공고 규칙 또는 사용자 정보 부족 | 제외하지 않고 “공고 확인 필요” |

실제 공고 5건을 `notice_rules.json`으로 구조화했다. 355개 재고 중 공고가 연결된 후보는 행복주택 6개, 청년 매입임대 19개, 일반 매입임대 구별 대기자 대상 256개, 재개발 7개, 통합공공임대 1개다. 공고가 연결돼도 사용자 프로필과 공적자료 조회가 없으면 자격은 `unverified`이며 임의로 확정하지 않는다.

### 3.4 모집공고 자격정보와 A1~A4 연결

모집공고에서 파싱한 자격정보는 별도의 설명 데이터로만 두지 않고 `tag/output/a-qualification-tags.json`의 매물별 `aTags`에 연결한다.

| 계층 | 산출 위치 | 연결 단위 | 예시 |
|---|---|---|---|
| A1 임대유형 | `aTags.a1RentalType` | 매물·공고 경로 | `rental_happy`, `rental_purchase` |
| A2 모집대상 | `aTags.routes[].a2SupplyTracks[]` | 공고 경로·공급트랙 | `target_youth`, `target_senior` |
| A3 자격규칙 | `aTags.routes[].a3QualificationRules` | 공고 경로·공급트랙 | `a3:age`, `a3:monthlyIncome` |
| A4 판정상태 | `aTags.a4OfferEligibility[]` | 공급행 | `unverified`, `conditional` |

```json
{
  "aTags": {
    "modelRole": "hard_filter_only",
    "scope": "notice_route_and_offer",
    "a1RentalType": {
      "tagId": "rental_happy",
      "label": "행복주택"
    },
    "routes": [
      {
        "routeId": "BMC-2026-153",
        "a1RentalTypeTagId": "rental_happy",
        "a2SupplyTracks": [
          {
            "trackId": "youth",
            "targetTagIds": ["target_youth"]
          }
        ],
        "a3QualificationRules": {
          "commonRuleIds": ["a3:housing_status"],
          "trackRuleIds": [
            {
              "trackId": "youth",
              "ruleIds": ["a3:age", "a3:monthlyIncome"]
            }
          ]
        }
      }
    ],
    "a4OfferEligibility": [
      {
        "offerId": "housing-id:offer:1",
        "status": "unverified",
        "matchedNoticeIds": ["BMC-2026-153"],
        "matchedTrackIds": ["youth"]
      }
    ]
  }
}
```

연결 원칙:

1. A2 모집대상과 A3 자격규칙을 매물 전체의 문자열 태그로 합집합하지 않는다.
2. `공고 경로 → 공급트랙 → 자격규칙 → 공급행 판정`의 적용 범위를 보존한다.
3. 화면·설명용 `qualificationDisplay`도 동일한 A1~A3 규칙에서 파생한다. 설명 문구를 별도의 판정 원천으로 사용하지 않는다.
4. 사용자 자격정보가 없으면 A4는 `unverified`다. 정보 부족을 `ineligible`로 바꾸지 않는다.
5. 명시적인 구조화 규칙 위반이 확인될 때만 `ineligible`로 제외한다.
6. A 태그는 취향점수에 더하지 않고 후보 생성 전 하드필터에만 사용한다.

현재 산출물에는 실제 매물 355개, 공고·유형기준 경로 365개, 공급행 4,398개가 들어 있다. 사용자 프로필을 넣지 않은 기본 산출에서는 4,398개 공급행 모두 `unverified`이며 이는 의도된 결과다.

### 3.5 태그에서 제외한 표현

다음 표현은 단일·고정 태그로 사용하지 않는다.

- `#소득150이하`: 공급유형, 가구원 수, 기준연도에 따라 달라진다.
- `#장기거주30년`: 계약기간·갱신조건을 공고에서 확인해야 한다.
- `#청약통장불필요`: 공급트랙별 예외와 우선순위 조건이 있을 수 있다.
- `#분양전환`: 실제 공고의 분양전환 조건과 시점 없이는 확정할 수 없다.

이 정보가 필요하면 공고별 버전이 붙은 구조화 규칙으로 저장한다. 정정공고가 있으면 최신 정정공고를 우선한다.

### 3.6 최종 공고 규칙

- `BMC-2026-153`: 2026 행복주택, 2026-07-27 신청 시작 예정, 6개 단지
- `BMC-2026-120`: 2026 1차 청년 매입임대, 접수 종료, 공급대상 19개 주소
- `BMC-2026-50`: 2026 일반 매입임대, 접수 종료, 9개 구·군 대기자 모집
- `BMC-2025-213`: 2025 재개발임대, 접수 종료, 7개 단지
- `BMC-2025-301`: 일광 통합공공임대, 접수 종료, 39A·59B 예비입주자

규칙 원본은 `tag/data/contracts/notice_rules.json`이다. 사용자 프로필을 받더라도 무주택·자산·소득·세대구성처럼 공적자료 확인이 필요한 조건은 `manual_review` 또는 `hard_then_official_review`로 유지한다.

### 3.7 산출 코드와 결과

- 코드: `tag/src/a-qualification.mjs`
- 결과: `tag/output/a-qualification-tags.json`

## 4. B. 주거물리 태그 최종안

### 4.1 역할

B는 “이 집을 좋아할 것인가” 이전에 사용자가 정한 현실 조건을 적용한다.

- 보증금·월세 상한
- 희망 면적과 방수
- 엘리베이터 필요
- 주차 필요
- 입주 가능한 주택형

이 조건으로 후보를 먼저 줄인 뒤 C/D 취향을 학습한다. 필터 통과 뒤에는 B를 큰 추천가중치로 다시 더하지 않는다. 사용자가 “신축을 더 선호한다”처럼 명시적으로 선택한 경우에만 작은 동률해소 조건으로 쓸 수 있다.

### 4.2 원천값을 우선 보존할 항목

- 전용면적 최소·최대
- 방수 최소·최대
- 준공일
- 총세대수
- 엘리베이터 유무
- 총주차대수
- 세대당 주차대수
- 층
- 난방방식
- 복도유형
- 개별 옵션
- 공용시설

표시 태그는 원천값을 요약할 뿐 원천값을 대체하지 않는다.

### 4.3 최종 파생 태그

#### 면적 밴드

- `area_under_25`: 25㎡ 미만
- `area_25_40`: 25㎡ 이상 40㎡ 미만
- `area_40_60`: 40㎡ 이상 60㎡ 미만
- `area_60_plus`: 60㎡ 이상

현재 `generated/housings.json`은 주택형 하나가 아닌 단지 전체 범위를 담고 있다. 범위가 여러 밴드에 걸치면 `areaBandAmbiguous=true`로 표시하며 단일 주택형 하드필터에 사용하지 않는다.

#### 방수

- `rooms_1`
- `rooms_2`
- `rooms_3_plus`
- `rooms_unknown`

단지 요약은 `roomRange`로 저장하되, 최종 원천의 9,022개 호별 사실은 `unitFacts`에 면적·방수·주택형·동·호 단위로 보존한다. 하드필터는 단지 범위가 아니라 `unitFacts`에 적용한다.

#### 준공연차

- `age_0_5`
- `age_6_10`
- `age_11_20`
- `age_21_plus`

연차는 실행연도를 기준으로 계산한다. 단순히 신축에 높은 점수를 주지 않고 사실 표시 또는 사용자가 명시한 동률해소에만 쓴다.

#### 단지 규모

- `complex_under_50`
- `complex_50_499`
- `complex_500_plus`

#### 엘리베이터

- `elevator_present`
- `elevator_absent`
- `elevator_unknown`

#### 세대당 주차

- `parking_1_plus`
- `parking_0_5_1`
- `parking_under_0_5`
- `parking_unknown`

`총주차대수 ÷ 총세대수`로 계산한다. 3을 초과하면 데이터 범위 또는 분모가 잘못 연결됐을 가능성이 커 `parking_unknown`으로 격리한다. 최종 전체 데이터에서 9개 후보가 이 기준 또는 값 결손으로 `parking_unknown`이다.

### 4.4 최종 데이터에 없어 비활성으로 확정한 B 태그

- 실제 층: 호명으로 추정하지 않음
- 난방방식
- 복도유형
- 지하주차장
- 전기차 충전시설

## 5. C. 입지·교통 태그 최종안

### 5.1 동해선 처리에 대한 최종 결정

동해선을 제외했던 이유는 기존 외부 역 파일이 부산교통공사 1~4호선 114개 역만 포함했기 때문이다. 동해선이 중요하지 않아서 제외한 것이 아니다.

이번 패키지에서는 한국철도산업정보센터의 전체 도시철도 역사 원문으로 교체했다.

- 부산교통공사 1~4호선: 114행
- 동해선: 23행
- 부산김해경전철: 21행
- 합계: 158행, 공식 환승 여부를 반영한 역 복합체 147개

최종 부산 전체 후보에서도 동해선과 부산김해경전철을 포함해 계산한다.

### 5.3 최종 C 배지

- `rail_walk_400`: 도시철도역 400m 이내
- `rail_walk_800`: 도시철도역 400m 초과 800m 이내
- `donghae_walk_800`: 동해선역 800m 이내
- `bgl_walk_800`: 부산김해경전철역 800m 이내
- `rail_transfer_walk_1000`: 환승역 1km 이내
- `bus_stop_walk_300`: 버스정류소 300m 이내

거리 표현은 현재 직선거리다. 실제 서비스에서는 “도보 5분”처럼 시간으로 바꾸지 말고 “직선거리 약 400m”처럼 표시한다. 보행 네트워크를 확보한 뒤에만 실제 도보거리·시간으로 승격한다.

### 5.4 거리 점수

반경 안 시설을 가까운 순서로 정렬하고 다음 값을 계산한다.

```text
접근량 a = Σ [0.85^i / (1 + 거리_i / 기준거리)]
점수 = 1 - exp(-a / 포화계수)
```

- 도시철도: 반경 800m, 기준거리 400m
- 환승역: 반경 1,000m, 기준거리 500m
- 버스정류소: 반경 400m, 기준거리 200m

후보 내 백분위가 아니기 때문에 후보 개수가 바뀌어도 점수 정의가 유지된다.

### 5.5 버스 태그의 한계

공식 부산 버스정류소 8,522개를 포함했다. 그러나 정류소가 가깝다고 해서 노선이 다양하거나 배차가 짧다는 뜻은 아니다.

`bus_stop_proximity`를 `버스 이용 편리`로 승격하려면 다음이 추가로 필요하다.

- 정류소별 노선·방향
- 평일/주말 및 출퇴근/심야 배차
- 첫차·막차
- 주요 목적지까지 환승 수와 소요시간

이 데이터가 생기면 `bus_service_access`를 별도 특징으로 만들고, 현재 정류소 근접값은 그 구성요소로 사용한다.

### 6.3 고정 거리 점수

C와 같은 거리감쇠 구조를 사용하되 업종별 시설 수가 다르므로 포화계수를 다르게 둔다.

```text
접근량 a = Σ [0.85^i / (1 + 거리_i / 기준거리)]
점수 = 1 - exp(-a / 업종별 포화계수)
```

시설이 매우 많은 업종은 포화계수를 크게 두어 시설 몇 개만으로 즉시 만점이 되지 않게 한다.

### 6.4 조용한 주거환경 산식

실측 소음데이터가 충분하지 않으므로 아래 대리지표를 쓴다.

```text
quiet =
  0.50 × (1 - 야간활기 점수)
  + 0.30 × (1 - 원천 인구격자 CDF)
  + 0.20 × 주거용도 점수
```

주거용도 점수는 주거지역이면 1, 그 외이면 0이다. 선도소프트 컬럼정의서를 다시 확인한 결과 `BSST_YN`은 ‘상권형성 여부’가 아니라 **버스정류장 여부**이므로 조용함이나 상업 혼재 판정에 사용하지 않는다. 태그 부여 기준은 0.55 이상이면서 주거지역인 경우다.

이 값은 **조용함 실측값이 아니다.** 서비스 문구도 “조용한 주변으로 추정돼요”, “야간업종과 생활밀도를 기준으로 본 조용함”처럼 한계를 밝혀야 한다.

### 6.5 공원 태그의 한계

부산 전체 공식 도시공원 652개를 사용한다. 현재는 대표 좌표 직선거리이므로 다음은 알 수 없다.

- 실제 출입구 위치
- 보행경로 단절
- 언덕·횡단보도
- 공원 시설 품질과 개방시간

따라서 “공원 산책 가까움”으로 표시하며 “도보 5분” 같은 단정은 하지 않는다.

### 6.6 의료 접근 태그

의료는 측정하기 쉽기 때문에 넣은 부가기능이 아니라 공공임대의 다양한 수요자에게 실질적으로 중요한 생활 기반시설이다. 2026년 6월 말 기준 건강보험심사평가원 전국 병·의원·약국 현황을 부산으로 필터링해 사용한다.

| 원자/결합 특징 | 대상 | 반경·기준 | 역할 |
|---|---|---|---|
| `pharmacy_access` | 약국 1,733곳 | 800m, 기준거리 400m | 일상 의료 구성요소 |
| `primary_care_access` | 의원·보건소·보건지소·보건진료소 2,743곳 | 1,000m, 기준거리 500m | 일상 의료 구성요소 |
| `medical_daily_access` | 위 두 점수의 기하평균 | 각 구성요소 0.55 이상, 결합 0.65 이상 | 명시적 선택 시 개인화 |
| `emergency_access` | 응급의료기관 29곳 | 5,000m, 기준거리 2,500m | 조건부 보조 순위·설명 |

```text
일상의료점수 = sqrt(약국접근점수 × 의원·보건기관접근점수)
```

약국 또는 1차의료기관 한쪽만 매우 가까운 곳을 “의료생활권 우수”로 과장하지 않도록 기하평균과 구성요소 하한을 함께 쓴다. 일반 병원, 종합병원, 상급종합병원은 규모만으로 일상적 1차의료 접근을 대신하지 않으므로 `primary_care_access`에서 제외했다. 응급의료기관은 전문 분류를 사용해 별도로 계산한다.

의료 점수도 현재는 대표 좌표 간 직선거리다. 진료과목, 운영시간, 휴일·야간 진료, 실시간 응급수용 가능 여부, 보행경사와 도로 단절은 알 수 없으므로 UI에서는 “가까움” 또는 “접근성”으로만 설명한다. 특히 `emergency_access`를 “응급상황에서 안전함”이나 “즉시 진료 가능”으로 표현하지 않는다.

### 6.7 대학가 생활권 태그

대학상권은 단순히 대학 대표주소가 가깝다는 사실만으로 확정하지 않는다. 한국대학교육협의회 2025년 전국대학및전문대학정보표준데이터 1,995건에서 부산 131건을 추출한 뒤 다음을 제외했다.

- 학부 생활권과 중복되는 대학원 102건
- 학생 유동을 대표하지 않는 사이버대학 2건
- 교육부 폐쇄명령을 받은 동부산대학교
- 영산대학교에 통합된 성심외국어대학의 과거 학교명

남은 부산 대면 대학·전문대학 대표 캠퍼스 25곳은 선도소프트 상가건물 도로명·지번주소와 정확주소로 결합했으며 좌표 결측은 0건이다.

```text
campus_access =
  대학 대표주소 거리감쇠 합을 1-exp(-a/0.7)로 변환

student_life_mix =
  0.30 × 카페
  + 0.30 × 외식
  + 0.20 × 편의점
  + 0.10 × 세탁
  + 0.10 × 문화

university_commercial_area =
  weighted_geometric_mean(campus_access, student_life_mix; 0.55, 0.45)
```

`대학가 생활권`은 다음 조건을 모두 만족할 때만 부여한다.

1. 최근접 대학 대표주소가 900m 이내
2. `university_walk_access` 0.43 이상
3. `university_life_mix` 0.60 이상
4. `university_commercial_area` 0.56 이상

전체 355개 후보 중 `대학 캠퍼스 가까움`은 107개, `대학가 생활권`은 73개에 부여됐다. 73개라는 수치는 매물 수이며 동일 건물·인접 주소가 여럿 포함될 수 있다.

이 태그는 **설명 전용 파생태그**다. 카페·외식·편의점·세탁·문화 원자점수로 이미 구성되므로 추천점수에 독립 가중치로 다시 더하면 같은 상권을 중복 가산한다. 개인화는 기존 원자축으로 수행하고 카드에는 “대학가 생활권 · 최근접 ○○대학교 약 000m(직선거리)”처럼 설명한다.

현재 좌표는 캠퍼스 경계나 출입구가 아니라 공식 표준데이터 대표주소다. 학생 수, 유동인구, 실제 보행거리, 여러 캠퍼스 중 표준데이터에 없는 부속 캠퍼스는 반영하지 않는다. 따라서 UI에서 “대학생이 많다”나 “도보 10분”으로 단정하지 않고 `대학가 생활권 추정` 또는 `대학 캠퍼스와 학생생활형 상권이 가까움`으로 표현한다.

## 7. 결합태그 최종안

### 7.1 역할과 계산

결합태그는 서로 다른 강점이 동시에 있을 때만 사람이 이해하기 쉬운 이름을 붙인다.

```text
결합점수 = 구성요소의 기하평균
부여조건 = 결합점수 0.65 이상 AND 모든 구성요소 0.55 이상
```

하나의 매우 높은 값이 다른 낮은 값을 완전히 덮지 못하게 구성요소 하한을 둔다. 필요한 값 하나라도 `null`이면 결합태그도 `null`이며 미부여한다.

### 7.2 최종 10개

| ID | 표시명 | 구성요소 |
|---|---|---|
| `rail_daily` | 역세권 생활편의 | 철도 접근 × 일상 필수시설 |
| `active_transit` | 대중교통형 액티브 라이프 | 철도 접근 × 운동시설 |
| `transit_quiet` | 교통도 챙긴 조용한 주거지 | 철도 접근 × 조용함 |
| `transit_park` | 역세권 공원생활 | 철도 접근 × 공원 |
| `quiet_green` | 조용한 숲세권 | 조용함 × 공원 |
| `daily_green` | 생활편의형 공원생활 | 일상 필수시설 × 공원 |
| `compact_rail` | 콤팩트 역세권 | 40㎡ 미만 확인 × 철도 접근 |
| `compact_daily` | 콤팩트 생활편의 | 40㎡ 미만 확인 × 일상 필수시설 |
| `recent_quiet` | 새집에 가까운 조용한 주거 | 준공 5년 이내 확인 × 조용함 |
| `culture_transit` | 대중교통형 문화생활 | 철도 접근 × 문화·여가 |

`일상 필수시설`은 아래처럼 만든다.

```text
0.45 × 마트 + 0.30 × 편의점 + 0.25 × 세탁·빨래방
```

`도시활동성`도 아래처럼 보조값으로 산출하지만 현재 최종 결합태그에는 직접 이름을 붙이지 않았다.

```text
0.30 × 카페 + 0.35 × 외식 + 0.20 × 야간활기 + 0.15 × 문화
```

### 7.3 A를 결합점수에 넣지 않는 이유

`청년 × 역세권` 같은 표현은 카드 제목이나 검색 문맥으로는 가능하다. 그러나 청년 공급이라는 사실이 그 집의 생활환경 점수를 높이지는 않는다.

따라서 A는 다음처럼만 사용한다.

- `청년 공급 · 역세권 생활편의`
- `고령자 공급 · 공원 산책 가까움`

실제 자격판정이 `unverified`라면 “신청 가능”처럼 표현하지 않는다.

### 7.4 B 결합의 보수적 조건

현재 B 면적은 단지 범위다. 따라서 `compact_*`는 단지의 최대면적이 40㎡ 미만일 때만 `compact_confirmed=1`로 둔다. 최대면적이 59㎡인 단지에서 일부 19㎡형이 있다는 이유만으로 단지 전체에 콤팩트 태그를 붙이지 않는다.

주택형별 면적이 제공되면 결합태그도 주택형 단위로 계산해야 한다.

### 7.5 추천점수 중복 방지

예를 들어 `rail_daily`가 붙은 매물은 이미 `rail_access`, `supermarket_access`, `cvs_access`, `laundry_access` 값을 갖는다.

```text
잘못된 계산:
추천점수 = 원자 특징 점수 + rail_daily 점수

올바른 계산:
추천점수 = 원자 특징 점수
추천 사유 = "역세권 생활편의"
```

## 10. 실행 방법

### 10.1 외부 원천을 갱신했을 때만 정규화

python3 tag/src/prepare-rail.py
node tag/src/prepare-shapefiles.mjs
python3 tag/src/prepare-medical.py --source "/path/to/전국 병의원 및 약국 현황 2026.6.zip"

철도 스크립트에는 `pandas`, `openpyxl`이 필요하다. 의료 스크립트는 Python 표준 라이브러리만 사용하며, 용량이 큰 전국 원본 대신 부산 정규화본만 저장소에 포함한다. 대학 스크립트는 공식 전국 JSON과 `data/out/gis.json`의 정확주소 좌표를 결합한다. 현재 `tag/data/external/`에는 이미 정규화된 JSON이 들어 있으므로 원천을 바꾸지 않았다면 이 단계는 생략할 수 있다.

node tag/src/run-all.mjs

## 13. 서비스 연결 방식

### 13.1 온보딩 전

1. 사용자 기본정보로 A의 명백한 부적격을 제외한다.
2. 예산·면적·방수·엘리베이터·주차 같은 B 하드조건을 적용한다.
3. 정보가 부족한 A는 `unverified`로 유지하고 확인사항을 표시한다.

### 13.2 A/B 가상 매물 취향 테스트

가상 매물 카드는 실제 후보의 가격·면적을 비교하는 화면이 아니라 C/D 취향축을 효율적으로 탐색하는 화면으로 사용한다.

예:

- A: 철도 접근·카페·외식
- B: 조용함·공원

선택 로그는 카드 이름이 아니라 카드가 가진 원자 특징 벡터의 차이로 학습한다.

```text
P(A 선택) = sigmoid(w · (x_A - x_B))
```

여기서 `w`가 개인의 C/D 선호 파라미터다. A/B 태그와 결합태그는 이 벡터에 넣지 않는다.

### 13.3 실제 후보 추천

1. A/B 필터를 통과한 실제 후보만 남긴다.
2. 사용자의 학습된 C/D 가중치와 실제 후보의 C/D 특징을 비교한다.
3. 결합태그를 추천 사유로 붙인다.
4. 원천 근거와 주의사항을 함께 표시한다.

결측 특징이 있는 후보는 결측을 0으로 대체하지 않는다. 현재 취향추천은 C/D 핵심근거가 모두 있는 179개를 정밀 순위군으로 사용하며, 나머지는 A/B 조건검색과 `추가 위치 확인 후보`로 제공한다.

### 13.4 지속학습

온보딩 뒤에는 사용자가 결정한 대로 **찜 행동만** 명시적 긍정 피드백으로 사용한다.

- 찜: 해당 실제 후보의 C/D 특징 방향으로 개인 가중치를 소폭 업데이트
- 찜 취소: 강한 싫어요가 아니라 신뢰도 낮은 약한 반대 또는 중립으로 처리
- 조회·스크롤: MVP에서는 학습에 사용하지 않음

한 매물에 여러 번 찜/취소를 반복해 가중치가 과도하게 변하지 않도록 사용자-매물별 최신 상태를 멱등적으로 반영한다.
