## 3. 데이터 정제 결과

### 3.1 인코딩과 헤더

부산도시공사 6종은 UTF-8 BOM과 CP949가 혼재한다. 인제스트는 UTF-8 유효성을 먼저 확인하고 실패 파일만 CP949로 읽는다.

다음 헤더는 canonical 이름으로 정규화한다.

- `전용면적(제곱미터)` → `전용면적`
- `가구인원수(명)` → `가구인원수`
- `표준보증금(원)` → `표준보증금`
- `표준임대료(원)` → `표준임대료`
- `평형타입` → `주택형`

날짜는 `YYYYMMDD`, `MM-DD-YYYY`, `YYYY-MM-DD`를 모두 ISO 날짜로 변환한다.

### 3.2 단지 요약과 호별 사실의 분리

단지 카드는 최소·최대 면적과 가격을 보여줄 수 있지만 하드필터는 단지 범위에 적용하면 안 된다. 예를 들어 면적 19~59㎡ 단지 전체를 `40㎡ 이상`으로 통과시키거나 제외하면 오류다.

따라서:

- 목록 요약: 단지별 최소·최대
- 실제 필터: `B.unitFacts`의 9,022개 호별 면적·방수·주택형
- 가격 필터: `A.offers`의 4,397개 순위·공급계층·소득구간별 가격행

으로 분리했다.

### 3.3 좌표

주택 원천에는 위·경도가 없다. 주택 주소를 외부 지오코딩 API로 전송하지 않고 선도소프트 상가-건물의 도로명주소를 로컬 결합했다.

| 좌표 품질 | 후보 수 | 처리 |
|---|---:|---|
| `exact_address` | 59 | 같은 도로명주소 상가-건물 좌표 |
| `road_nearest` | 246 | 같은 도로에서 건물번호가 가까운 주소점 |
| 미확보 | 50 | C/D 점수 없음, A/B 재고에는 유지 |

`road_nearest`는 정확한 건물점이 아니므로 거리 근거에 품질 플래그를 남긴다. 좌표 근사는 추천 프로토타입에는 사용하되 실제 운영 배포 전 공식 건물 좌표로 교체하는 것이 바람직하다.

## 5. 최종 태그 체계

### 5.1 A — 자격·유형·공고

A는 추천점수가 아니라 하드필터와 확인 상태다.

핵심 필드:

- 임대유형
- 공급계층·순위
- 공고 ID와 기준일
- 신청기간과 현재 상태
- 신청 방식: 개별 주택, 단지·주택형, 구별 대기자
- `unitSelectable`
- 자격 상태: `likely_eligible`, `conditional`, `ineligible`, `unverified`
- 재고 상태: `open_for_application`, `upcoming_application`, `closed_reference`, `inventory_only`

무주택, 세대구성, 공적 소득·자산 조회처럼 서비스 입력만으로 확정할 수 없는 조건은 수동·공식 심사 대상으로 유지한다.

### 5.2 B — 주거물리

B는 기본 입력 단계의 하드필터와 사실표시다.

- 호별 전용면적·방수·주택형·동·호
- 순위·공급계층·소득구간별 보증금·월임대료

### 5.5 개인화 기본 8축과 조건부 의료축

2. 카페 선택지
3. 운동시설 접근
4. 슈퍼마켓 접근
5. 외식 선택지
6. 문화·여가 접근
7. 조용한 주거환경 추정
8. 공원 접근

A와 B는 필터, 결합태그는 설명이므로 개인 취향점수에 더하지 않는다. 의료는 데이터가 없어서 보류하는 항목이 아니라 **선택형 개인화 특징**으로 추가한다. 사용자가 기본입력 또는 취향보정에서 의료 접근을 중요하다고 명시할 때 `medical_daily_access`를 활성화하며, 필요할 경우 `emergency_access`를 보조한다. 연령·임대유형만으로 의료 선호를 자동 추정하지 않는다.

## 6. 점수와 추천

### 6.1 공간 특징 점수

```text
접근량 a = Σ [0.85^i / (1 + 거리_i / 기준거리)]
점수 = 1 - exp(-a / 포화계수)
```

후보군 백분위가 아니라 고정 함수다. 새 후보가 추가돼도 같은 시설 구성은 같은 점수를 갖는다.

### 6.2 온보딩 개인 선호학습

가상 매물 A와 B의 C/D 특징 차이를 이용한다.

```text
P(A 선택) = sigmoid(w · (x_A - x_B))
```

- `w`: 사용자별 기본 8축 선호 파라미터 + 직접 활성화한 경우의 의료 파라미터
- 선택할 때마다 로지스틱 SGD로 소폭 갱신
- 비슷함·둘 다 아님은 상대선호 라벨로 쓰지 않음
- 이전 질문 수정 시 남은 로그를 처음부터 재생
- 가격·면적·방수는 비교 전에 하드필터하고 가상 비교에서 통제

### 6.3 실제 후보 추천

1. A에서 공고·자격 상태를 확인한다.
2. B에서 예산·면적·방수·필수시설을 호·공급행 단위로 필터한다.
3. C/D 근거가 완전한 후보에 사용자 선호 적합도를 계산한다.
4. 결합태그로 추천 이유를 만든다.
5. `closed_reference`와 `inventory_only`를 현재 신청 가능한 주택처럼 표시하지 않는다.
6. 좌표 근사, 직선거리, 조용함 대리지표를 감수할 점으로 표시한다.

## 10. 최종 결정

추가 데이터가 더 들어오지 않는다는 전제에서 태그 정의는 다음처럼 동결한다.

- A: 공고·자격·재고 상태, 점수 0
- B: 호·공급행 단위 하드필터와 사실표시, 원칙적으로 점수 0
- C/D: 개인 취향학습과 추천의 원자 특징
- 결합태그: 설명 전용, 점수 0
- 개인화 벡터: 기본 C/D 8축 + 명시적 선택형 `medical_daily_access`
- 응급의료: 명시적 선택 시 보조 순위·설명 근거
- 시장·종합상가: 데이터 정의 부족으로 비활성
- 버스: 정류소 근접만 표시
- 조용함: 대리지표임을 명시
- 인구 연령·성별 구성: 주거지 선호 점수에 사용하지 않음
- 현재 신청 가능성과 보유 재고를 반드시 분리
