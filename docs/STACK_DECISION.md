# 스택 결정 기록 — self-host 전통 구성 vs Supabase + Vercel

> 상태: **결정됨** (2026-07-07)
> 범위: 백엔드·DB·배포 인프라 (프론트 React+Vite는 불변)
> 관련: [`PRODUCTION_PLAN.md`](./PRODUCTION_PLAN.md) P2·P7, [`HARNESS_DESIGN.md`](./HARNESS_DESIGN.md)

---

## 1. 맥락

BMC 취향 기반 공공임대주택 추천 서비스. 현재는 프론트 단독 프로토타입(목데이터)이며, 실데이터 수용(P0)과 백엔드 착수(P2)를 앞두고 인프라 스택을 확정해야 한다.

다른 프로젝트에서 쓰던 **Supabase + Vercel** 매니지드 구성과, 플랜에 제안된 **NestJS + 자체호스팅 PostgreSQL/PostGIS + Docker** 전통 구성 중 무엇으로 갈지가 쟁점이었다.

당면 목표는 **데모 시연**이며, 시연은 발표자가 직접 구동하는 형태(로컬/노트북 기준)를 전제한다.

---

## 2. 고려한 옵션

### 옵션 A — Supabase + Vercel (매니지드)
- Supabase = 매니지드 PostgreSQL(PostGIS 확장 가능) + Auth + Edge Functions.
- 프론트는 Vercel에 git push 배포.
- 상시 무료 티어로 항상 떠 있는 공유 링크를 얻는다.

### 옵션 B — NestJS + PostgreSQL/PostGIS + Docker (self-host) ✅ 채택
- `docker compose`로 web·api·db·redis를 한 번에 구동.
- API 서버(NestJS), DB(PostGIS), 배포 대상을 직접 소유·제어.

---

## 3. 비교

| 기준 | A. Supabase + Vercel | B. self-host (채택) |
|---|---|---|
| DB / 지리연산 | Postgres + PostGIS (확장 켜기) | Postgres + PostGIS (동일) |
| 로컬 개발 부담 | 낮음 (매니지드) | **낮음** — `docker compose up` 한 줄로 PostGIS 기동 |
| 상시 링크 유지 부담 | **매우 낮음** (무료·항상 켜짐) | 있음 (VM·배포·HTTPS·백업 관리) |
| 노트북 시연 적합성 | 가능 | **가능** — 오프라인에서도 완결 구동 |
| 공공 개인정보 규제 | 해외 사업자 매니지드 → 데이터 소재지·규제 별도 확인 필요 | **소유·통제 명확** (규제 대응 유리) |
| 스토리텔링(아키텍처 서사) | "매니지드에 얹었다" | **"수집→정규화→지리연산→추천을 직접 설계했다"** |
| 공공 운영 배포로의 연속성 | 재설계 가능성 | **그대로 연장** |

핵심: DB·PostGIS 선택은 두 옵션이 동일하다. **Supabase는 곧 PostgreSQL**이므로 "지리연산 때문에 Postgres"라는 논리와 충돌하지 않는다. 갈리는 지점은 DB가 아니라 **운영 소유권·규제·서사**다.

---

## 4. 결정

**옵션 B(self-host 전통 구성)를 채택한다.**

## 5. 근거

1. **데모 형태가 로컬 구동이라 전통 구성의 주된 약점이 사라진다.** 전통 구성의 실질 부담은 "만드는 것"이 아니라 "상시 링크를 살려두는 것"인데, 노트북 시연에는 상시 링크가 필요 없다. Docker가 PostGIS 설치 부담을 `docker compose up` 한 줄로 없애므로, 로컬 개발·시연 부담은 매니지드와 큰 차이가 없다.

2. **스토리텔링에 유리하다.** 이 서비스의 핵심 가치는 "주소 → 좌표 → 반경 내 POI 밀집도 → 취향 가중 추천"이라는 데이터 파이프라인 그 자체다. 수집·정규화·지리연산·스코어링을 직접 설계·소유하면 시연에서 "우리가 이 추천을 어떻게 만들어내는가"를 끝단까지 서사로 보여줄 수 있다. 매니지드에 얹으면 이 서사가 블랙박스로 가려진다.

3. **공공서비스 규제와 정합적이다.** 부산도시공사(공기업) 서비스는 소득·자산·본인인증 등 민감 개인정보를 다룬다. 데이터 소재지·접근통제를 직접 소유하는 편이 공공 규제 대응에 유리하며, 해외 매니지드 사용 가부를 지금 판단하지 않아도 된다.

4. **운영 배포로 버려지지 않고 이어진다.** 데모용 self-host 구성이 이후 실제 공공 운영 배포(P7)로 그대로 연장된다. 시연을 위한 작업이 폐기물이 아니라 운영 기반의 선투자가 된다.

## 6. 감수하는 트레이드오프

- 상시 공유 링크가 필요해지면 별도 호스팅(VM·배포 파이프라인)을 세워야 한다 — 데모 단계에서는 불필요하므로 유예한다.
- NestJS 스켈레톤 보일러플레이트(초기 1~2일)가 매니지드 자동 API보다 더 든다 — 서사·제어권의 대가로 수용한다.

## 7. 재검토 조건

아래 중 하나라도 발생하면 이 결정을 다시 검토한다.

- 데모 목표가 "발표자 로컬 구동"에서 "이해관계자에게 보내는 상시 링크"로 바뀔 때.
- 상시 운영 인프라를 관리할 인력·비용이 없다고 판명될 때 → 매니지드로 재검토.
- 공공 개인정보의 해외 매니지드 사용이 규제상 명시적으로 허용/금지로 확정될 때.
