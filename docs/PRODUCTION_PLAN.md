## 1. 문제와 접근

### 1.1 문제 정의

- **배경:** 부산 인구 지속 감소(최근 10년 약 24만 명↓)·지역 소멸 위기. 낮은 소득 대비 과도한 주거비 → 외곽 이탈, 공공임대 당첨자 **입주 포기율 약 50%**.
- **문제:** ① 공급자 중심 일방향 정보(면적·보증금 등 정량 조건만) ② 주변 상권·편의시설 정보 부재 ③ 개인 라이프스타일 기반 추천 부재.
- **해결:** 시민이 선호하는 **생활 인프라와 취향**을 반영한 수요자 맞춤 추천. 공간 범위는 부산 전역(**주택 355단지 · 15개 구·군**).

### 1.2 제공 데이터 (2소스)

| 소스               | 데이터                                                  | 형식                    | 반영                                                        |
| ------------------ | ------------------------------------------------------- | ----------------------- | ----------------------------------------------------------- |
| **부산도시공사**   | 주택정보 2종 + 유형별 보증금·임대료 4종, 참고자료 모집공고 | CSV(CP949), 공고 hwpx/pdf | 부산 전역 355단지·15개 구                                   |
| **㈜선도소프트**   | 상가-건물 융합, 5대 업종-인구 밀집도, 상권·용도지역 융합  | SHP(좌표 내장)          | 상가-건물 16.1만 · 밀집도 격자 8.0만 · 용도지역 격자 2.9만 |

**상권 추천의 근거 데이터는 선도소프트 GIS다.** POI를 자체 수집하지 않고 제공된 상권 융합정보를 1차 소스로 쓰며, 외부 공개데이터는 GIS가 덮지 않는 축(공원·교통)만 보강한다. 주택 CSV는 좌표가 없어 지오코딩이 필요하지만 GIS는 좌표가 내장돼 지오코딩 대상이 아니다.

## 2. 아키텍처

**운영** — 정적 배포. 런타임에 백엔드·DB를 쓰지 않고, 서버가 필요한 지점은 AI 키를 숨기는 Pages Function 하나뿐이다.

```
[React SPA] ──> Cloudflare Pages (정적)
   │  TanStack Query · Zustand · react-router
   │  Naver Maps JS API
   │  generated/*.json (인제스천 산출물을 번들에 동봉)
   └──> POST /api/search/nl ──> Pages Function ──> Claude API (실패 시 Gemini API)
```

**개발·검증** — 백엔드·PostGIS 경로를 확인할 때 쓰는 풀스택 구성.

```
[React SPA] ──HTTPS──> [NestJS REST]
                         ├─ housings · meta · search(NL)
                         └─ Prisma ──> [PostgreSQL + PostGIS]
                                          ↑
        [배치/ETL] BMC 주택 CSV + 선도소프트 GIS(SHP) + 외부 공개데이터
```

프론트는 `VITE_API_BASE_URL` 하나로 소스를 전환한다 — 비우면 MSW 목서버가 `generated/housings.json`을 서빙하고, 채우면 실 API로 붙는다. 배포 절차는 [README](../README.md#배포와-로컬-실행).

**왜 정적 배포인데 NestJS·PostGIS를 갖고 있나.** 매니지드(Supabase 등)에 얹지 않고 자체 구성을 택한 이유는 두 가지다. ① 이 서비스의 핵심 가치가 "주소 → 좌표 → 반경 내 상권 밀집도 → 취향 가중 추천"이라는 **지리연산 파이프라인 그 자체**여서, 수집·정규화·공간조인·스코어링을 직접 소유해야 근거를 끝단까지 설명할 수 있다. ② 공기업 서비스로 전환되면 소득·자산·본인인증 등 민감 개인정보를 다루게 되는데, **데이터 소재지·접근통제를 직접 소유하는 편이 규제 대응에 유리하다**. 지금은 앱이 서버 없이 완결되므로 정적 배포로 링크를 제공하고, 이 구성은 런타임 DB·인증이 실제로 필요해지는 시점에 그대로 세운다.

### P0. 데이터 인제스천 ✅

원천 CSV 6종(주택정보 2 + 가격 4)을 유형별 어댑터가 정규화해 canonical 스키마로 넘긴다. 어댑터가 흡수하는 표기 함정: CP949 인코딩, 세대수·주차대수의 천단위 콤마, 전용면적 트레일링 공백, 방수 zero-pad, 날짜 포맷 혼재(`YYYYMMDD` vs `MM-DD-YYYY HH:mm:ss`), 금액 단위 원. 주소는 VWorld·Kakao로 지오코딩하고 결과를 캐시해 재실행 비용을 없앴다. 스키마 명세는 [`DATA_SCHEMA.md`](./DATA_SCHEMA.md), 전처리 결과는 [`데이터_전처리_품질보고서.md`](./데이터_전처리_품질보고서.md).

**실데이터 교체점은 `data/source/`의 CSV + 유형별 어댑터(`scripts/ingest/adapters/`) 한 곳뿐이다.** 새 CSV가 들어오면 그 한 곳만 바꾸면 끝단까지 흐르고, 뒤 단계·UI는 무변경이다. 산출물은 앱이 읽는 `frontend/src/generated/housings.json`과 DB 시드 입력 `data/out/canonical.json` 두 갈래이며, 같은 스키마를 P2에서 DB로 승격했다.

### P1. 프론트엔드 기반 ◐

react-router v7 라우팅(핀별 상세 라우팅), TS strict + canonical 타입을 `@bmc/shared-types`로 승격(프론트·백엔드·인제스천 공유), 단일 Context 해체 후 서버상태(Query)/UI상태(Zustand) 분리, 로딩·빈·에러 3-상태 UI 표준화, Tailwind v4 `@theme` 토큰 + `components/ui` 공통 컴포넌트로 전 화면 치환. 접근성은 aria-label·`:focus-visible`·시맨틱 태그까지 1차 반영.

**잔여:** axe 자동검증, RTL 컴포넌트 렌더 테스트·Playwright E2E.

### P2. 백엔드 기반 ◐

PostgreSQL 16 + PostGIS, Prisma(complexes/units/pricing), `GET /api/housings`·`/:id`·`/meta/filters`, `POST /api/search/nl`. `docker-compose.yml`은 db(healthcheck)·api·redis(profile) 구성이며 **실행검증 통과** — compose up → `db:push` → `db:seed` → `GET /api/health` 200 → housings 목록·상세·필터 정상.

**잔여:** 프론트–백엔드 실연결(현재 프론트 로컬 계산), Prisma Migrate 이력화, 환경 분리·운영화.

### P3. 상권 GIS & 추천 엔진 ◐

**발제사 데이터 활용의 핵심 단계.** 선도소프트 SHP 3종을 부산 전역으로 적재하고(shpjs가 EPSG:5186/5179 → 4326 재투영, bbox 가드로 검증, 재실행 멱등), KSIC 업종코드를 원자 8피처에 매핑했다.

- **2단계 구조** — 하드 필터(자격·예산·지역·유형·준공·면적·방수) → 소프트 랭킹(취향 적합도).
- **원자 8피처** — `rail_access, cafe_choice, fitness_access, supermarket_access, restaurant_choice, culture_access, quiet_residential, park_walk`. 단일 원천은 `@bmc/shared-types`의 `PREFERENCE_FEATURES`.
- **고정 거리감쇠** — `a = Σ 0.85^i/(1+d_i/기준거리)`, `점수 = 1 - exp(-a/포화)`. 후보군 백분위가 아닌 **절대 적합도**라 후보 풀이 바뀌어도 시설 구성이 같으면 같은 점수다. GIS 미커버·결측은 0점이 아니라 `null`.
- **취향 적합도** — 관측된 피처만 `Σ|w|·fit / Σ|w|`(결측은 분자·분모에서 동시 제외). `w`는 온보딩 pairwise가 학습한 가중치.
- **설명가능성** — 기여 상위 피처를 실제 거리·개수 근거와 함께 제시("가까운 역 ○○ 직선 320m", "주변 시설 12곳") + **결합태그 10종**(설명 전용, 추천점수 기여 0).
- **엣지** — 콜드스타트 warm-start prior, 0건 완화 제안(지역→준공→예산), 낮은 커버리지 후보 분리 표시.

LIVE 경로: `tag/` 파이프라인 → `preference-features.json`(355후보 8축) → 프론트 `rankByLearnedPreference` → 지도·홈. 검증은 `tag/test/pipeline.test.mjs`. 공식·파라미터 정본은 [최종기획안](./공공임대_취향추천_최종기획안.md) §7~8과 [태그가이드](../tag/최종_태그_체계_및_산출가이드.md) §5~7.

**잔여:** culture 축이 GIS에 서점만 있어 빈약 — 공공 문화시설 외부데이터 보강 검토. 골든 테스트(고정감쇠 수기 재현).

### P4. 사용자 도메인 ✅ (계정 없음)

전 화면 공개, 라우트 가드 없음. 첫 진입 팝업이 "개인정보를 수집·보관하지 않고 저장은 이 브라우저에만"임과, AI 검색을 쓸 때만 문장과 조건·관심 목록 요약이 외부 AI로 전송됨을 고지한다. 취향·필터 조건과 관심목록은 localStorage에 영속하고, 신청 자격은 범주형 값만 보관해 개인 식별정보를 남기지 않는다. 찜 행동 기반 취향 정교화(β≤0.25)는 첫 찜 시점에 on/off를 한 번 묻는다(기본 OFF).

### P5. AI 자연어 검색 ◐

Claude Sonnet 5의 structured outputs로 필터 스키마(예산·지역·유형·준공·면적·방구조 + 태그 가중치 + `unresolved`)를 강제한다. 파싱 결과는 **제거 가능한 조건 칩 + "이 조건으로 N곳" 확인 UI**로 보여준 뒤 확정 시에만 지도에 적용한다.

- **개인화** — 현재 필터를 프롬프트에 첨부하고 파싱 결과를 기존 조건 위에 **병합**한다(문장에 없는 축은 유지). 관심목록은 "관심 3곳 · 주로 수영구 · 신축 위주"처럼 압축 요약해 컨텍스트로 넘긴다.
- **멀티턴 되묻기** — 취향이 막연할 때 AI가 짧은 질문 + 탭 가능한 보기(각 보기 = 8피처 가중치)를 내고, 답을 태그에 누적해 다음 턴에 같은 질문을 반복하지 않는다. 이전 대화(최근 12턴)를 모델에 함께 넘겨 앞 답변을 이어받아 묻는다. 모델이 되묻기를 빠뜨리면 카테고리별 고정 질문이 이어받는다. 보기는 최대 4개, 되묻기는 대화당 최대 5회다. 5번째 질문에 답하거나 사용자가 "이제 결과 볼래요"를 누르면 되묻지 않고 대화 전체로 취향 결론을 낸다.
- **원문 안전망** — 되묻기를 낼 때도 문장에 명시된 조건은 함께 추출하게 프롬프트로 강제하고, 모델이 빠뜨린 방 구조·신축·구/군(줄임말 포함)·보증금·월세 상한은 클라이언트가 원문에서 보강한다(모델 값 우선).
- **안전·비용** — 입력 검증(300자 상한), 모델 출력 zod 재검증을 둔다. 백엔드는 여기에 IP당 슬라이딩 윈도우 레이트리밋과 동일 요청 캐싱(10분 TTL)을 더한다. 배포 환경(`pages.dev`)에는 Cloudflare Rate limiting 규칙을 걸 수 없어서 비용 상한은 Claude Console 월 사용 한도가 담당한다. API 키는 서버(Pages Function 시크릿·백엔드 env)에만 두고 브라우저는 항상 프록시를 거친다.
- **폴백** — `GEMINI_API_KEY`가 설정돼 있으면 Claude 호출이 실패할 때(사용 한도 소진·장애·거절) Gemini로 다시 요청한다. 한도는 Claude Console의 월 사용 한도로 정한다. 두 모델이 모두 실패하면 대화창에 잠시 후 다시 물어봐 달라는 안내를 띄우고, 답하던 보기를 다시 보여 준다.

**잔여:** 비용 모니터링.

### P6. 국내 지도 ◐

Leaflet/OSM → Naver Maps JS API(NCP) 전환. `useNaverMap`이 기존 훅과 동일 계약(컨테이너 ref + 마커 데이터)이라 화면 수정 없이 교체됐고 Leaflet 의존을 전면 제거했다. 픽셀 격자 **개수 클러스터**(줌 반응)·마커 클릭 선택·리스트=화면 내 매물 연동까지 완료. 상권 밀집도 히트맵은 이산 매물 수를 직관적으로 보여주는 클러스터가 데이터 성격에 더 맞아 미채택.

**잔여:** 서버 bbox 조회(`GET /housings?bbox=…`).

### P7. CI ⬜

lint·typecheck·test·build 파이프라인 미착수. 현재는 Husky pre-commit(`lint` + `typecheck`)이 대신한다.

## 4. 취향 온보딩

가중치를 직접 조절하게 하지 않고, 가상 생활권 A/B 비교로 8축 가중치를 추정한다.

```
Setup(하드필터) → Swipe(가상 매물 A/B) → Prefill(취향 진단·직접 보정)
```

로지스틱 갱신 `w ← (1-ηλ)w + η(y-p)·diff`, 이전 질문 재계산 포함. 문항은 핵심 5회 + 사용자 선택 추가. 이후 찜 행동으로 β≤0.25 범위에서 정교화한다. 설계 정본은 [최종기획안](./공공임대_취향추천_최종기획안.md) §6~7.

## 5. 프로덕션 연장 시 과제

현재 배포 범위 밖의 항목. 실서비스로 전환한다면 필요한 것들이다.

- **인증·신청** — Kakao OAuth + JWT/세션, 본인인증, 청약 신청 실연동(현재는 BMC 청약센터로 위임).
- **알림** — 모집공고 웹푸시·알림톡.
- **운영** — 환경 분리, DB 마이그레이션 자동화, 백업/DR, 관측성(로깅·트레이싱·대시보드).
- **컴플라이언스** — 개인정보처리방침, 시크릿·CORS·CSRF, KWCAG 접근성 전면 대응.
- **데이터 운영** — BMC 실데이터 갱신 주기·전달 방식 협의, 단지 식별자 확보(현재 `임대주택명`↔`사업지구` 문자열 매칭 의존).
